## 写作约束（适用于全文，违反会导致读者模拟扣分）

1. **技术术语首次出现时，必须用读者已知的事物解释。** 你是为用户自己做的调研，基于你对用户的了解（记忆+知识库）写报告。如果读者不是用户本人，在 intent_doc.json 的 v07.reader_model 中声明。
2. **每个表格/图表前必须有一句话说明"读者看完该理解什么"。** 写不出这句话的表格删掉——它是噪音。
3. **核心章节用"已知（读者经验）→桥梁（类比过渡）→未知（技术判断）"结构展开。** 不要一上来就给术语和架构图。
4. **概念类型决定表达方式。** 层级关系不用表格（用树状结构），时序关系不用表格（用流程），因果关系不用表格（用因果链）。表格只用于对比。
5. **写完后自检：读者能用自己的话复述 2-3 个核心判断吗？** 如果不能，重写。
6. **禁止把以下内容当叙事：** schema 名词、文件路径、内部步骤编号、统计描述当结论、术语当标签不建语境。
7. **色彩来自结构化块，不来自 inline code（强制执行标准）。**

   - **禁止**：正文段落中使用反引号包裹技术术语。inline code 渲染为带背景+边框的彩色药丸，密集出现破坏阅读节奏。全文反引号数量应为 0（代码块除外）。

   - **必须**：色彩节奏通过穿插大尺度结构化块实现。每份报告必须包含：

     - 引用块（markdown 的 `> ` 引用，渲染为 aside/blockquote）：8-12 个，用于章节开头的方法论声明、原文引用、注意事项

     - 表格：8-12 个，用于对比类信息、索引类信息、陈列类信息（带来源/证据列）

     - strong 段首标签词：100+ 个，格式为`**标签词**：正文内容`，服务于扫读（不是包裹技术术语）

   - **参考基准**（Lev8 报告）：0 个 inline code，9 个 aside.note，161 个 strong，12 个 table——段落干净，色彩来自大尺度结构化块。

   - **技术术语处理**：用纯文本（如 harness、Agent Loop），不用反引号。如需强调用 strong（如 **harness**），但 strong 应优先用作段首标签词而非术语强调。
