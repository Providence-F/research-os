# Research OS 使用说明 v1.2

> **唯一入口**：Agent 拿到 Research OS 时，必须先读本文档。
> 本文档同步到 Research OS v1.1 的真实状态。
> 如果本文档和其他文件冲突，以本文档为准。

---

## 1. Research OS 是什么

Research OS 是一个**深度调研工作流系统**。给定一个研究主题，它会引导你走完"任务定义 → 候选源采集 → 证据矩阵 → 假设账本 → 核心对象直采 → 多 Agent 分析 → 反方审计 → 独立审计 → 读者模拟 → 写-读-改闭环 → 最终报告 → HTML 可视化"的完整链路，产出一份有信任度保证的深度报告。

**设计哲学**：**Smart Agent. Dumb Tools.**
- 工具只做机械检查（存在性、字数、格式、字段值非空、必须结构正则匹配）
- 语义判断（好不好、要不要重写、质量高低）交给 Agent
- 工具不硬编码项目特定信息，不用阈值做语义决策

**核心原则**：内部文件服务可信度，最终报告服务读者。

## 4. 强制执行顺序（15 步 + 6 个门禁）

Agent 必须按以下顺序执行，每步完成后跑 `validate_research_project.py` 检查。

**完整流程详见 [`14-研究执行状态机.md`](14-研究执行状态机.md)**。本节为摘要。

| 步骤 | 名称 | 驱动 | 产物 | 门禁 |
|---|---|---|---|---|
| 0 | 脚手架 | 工具 | 目录结构 | 无 |
| 1 | 路由 | Agent 显式选择 | research_mode 字段 | 无 |
| 2 | 任务卡 | Agent | task-card.md | 字段值非空 |
| 3 | 调研方案 | Agent | research-plan.md | 字段值非空 |
| 4 | 候选源 | Agent | candidates.md + discarded.md | 存在性 |
| 5 | 证据矩阵 | Agent | evidence_matrix.md | 存在性 |
| 6 | 假设账本 | Agent | hypothesis_ledger.json | 字段值非空 |
| **6.5** | **核心对象直采** | **Agent** | **core_objects_fetch_log.md** | **强制门禁+URL≥3+对象≥3** |
| 7 | 多 Agent 分析 | Agent | 4 个分析文件 | 依赖 6.5 + 5 |
| 8 | 反方审计 | Agent | red_team.md | 字符数≥300 |
| 9 | 最终报告草稿 | Agent | final-report.md | URL≥5+数据点≥10+章节≥5 |
| **9.5** | **独立审计** | **审计 Agent** | **audit_report.md** | **5 问全 PASS** |
| 10 | 读者模拟 | 审计 Agent | reader_diagnosis.json + reader_feedback.md | 强制门禁 |
| **10.5** | **写-读-改闭环** | **工具+Agent** | **rewrite_instructions.json + iteration_state.json** | **通过或 max_iter** |
| 11 | 溯源清单 | Agent | trace-manifest.json | 存在性 |
| 12 | 视图模型 | Agent | view-model.json | 存在性 |
| 13 | HTML 构建 | **工具** | index.html | **禁止模式+必须结构检查** |
| 14 | 验证 | 工具 | validation_report | 全部检查 |
| 15 | 发布 | 工具 | 桌面副本 | 无 |

### 6 个强制门禁（v1.1）

| 门禁 | 触发 | 要求 | 失败后果 |
|---|---|---|---|
| 1. 核心对象直采 | 步骤 7 前 | log 存在 + 字符数≥200 + URL≥3 + 对象≥3 + 前置步骤 2/3 done | 不能进入步骤 7 |
| 2. 独立审计 | 步骤 9 后 | audit_report.md 存在且 5 问全 PASS | 不能进入步骤 10 |
| 3. 读者模拟 | 步骤 9.5 后 | reader_diagnosis.json + reader_feedback.md 存在 | 不能进入步骤 10.5 |
| 4. 写-读-改闭环 | 步骤 10 后 | rewrite_instructions.json 生成 + Agent 执行重写 | 不能进入步骤 11 |
| 5. HTML 禁止模式 | HTML 构建后 | aside.toc 无 overflow-y:auto + source-section div 正确闭合 | HTML 重构 |
| **6. HTML 必须结构**（v1.1 新增） | HTML 构建后 | **9 项必须结构全部存在**（page-shell/aside.toc/vm-hero/hero-verdict/reading-progress/section.chapter/Lora/#faf9f5/#b85b44） | **HTML 重构** |

**门禁 6 的设计原理**：v1.0 之前验证器只检查"禁止什么"（不能有 overflow-y:auto），不检查"必须有什么"（必须有 aside.toc）。这导致 Agent 手写 HTML 缺失关键结构时验证器无法发现。v1.1 新增 9 项必须结构检查，这些检查是机械的（正则匹配字符串是否存在），不是语义判断，符合 Dumb Tools 原则。

## 8. 验证器 v1.2（27 项检查）

```bash
python validate_research_project.py "项目路径"
```

### v0.6 保留检查（7 项）

1. 文件存在性
2. 最小字符数
3. 状态-产物一致性
4. 强制门禁（核心对象直采、独立审计、读者模拟）
5. 来源标注格式
6. HTML 存在性 + reader-first
7. 版本一致性

### v0.7 新增检查（7 项）

1. **JSON 字段值非空**（intent_doc/hypothesis_ledger/candidate_pool）
2. **task-card 字段值**（调研对象/决策目的/读者画像/核心问题）
3. **步骤依赖**（step N done → 依赖项必须 done）
4. **内容深度指标**（URL/数据点/章节数）
5. **HTML 禁止模式**（overflow-y:auto / div 未闭合）
6. **核心对象提及次数**（从 task-card 读取声明）
7. **前置门禁**（核心对象直采前必须完成任务卡和研究计划）

### v1.0 新增检查（2 项）

8. **view-model reader-facing**（hero 字段检查）
9. **行动方案比例**（≥15%）
10. **LaTeX 公式渲染**（MathJax/KaTeX 存在）

### v1.1 新增检查（1 项，含 9 个子检查）

11. **HTML 必须结构**（check_html_required_structures）
    - `.page-shell` 双列布局
    - `<aside class="toc">` 固定侧栏
    - `.vm-hero` Hero 区
    - `.hero-verdict` 一句话结论
    - `.reading-progress` 阅读进度条
    - `<section class="chapter">` 章节结构
    - `Lora` 衬线字体
    - `#faf9f5` 米色背景
    - `#b85b44` 暖砖红 accent

### v1.2 新增检查（3 项）

术语科普门禁——解决"知识的诅咒"（Agent 默认读者已知行业术语）：

11. **concept_ladder_seed**：当 `concept_ladder_needed=true` 时，seed 列表 >= 3 个术语
12. **reader_model**：当 `concept_ladder_needed=true` 时，reader_model.background 非空
13. **term_explanation_coverage**：seed 中每个术语在 final-report 首次出现位置附近是否有解释性内容（blockquote/类比/定义等标记）

**设计原理**：这三个门禁解决"后置验证"范式的根本缺陷——原来术语解释完全依赖 Agent 自觉，验证器不检查。现在从"用户读完报告发现术语没解释→打补丁"变为"验证器机械拦截→Agent 必须在写报告前声明要解释哪些术语"。

### v1.1 Dumb Tools 合规说明

新增的 HTML 必须结构检查是**机械的正则匹配**（字符串是否存在），不是语义判断：
- ✅ 检查 `class="page-shell"` 是否存在于 HTML 中 → 机械检查
- ✅ 检查 `Lora` 是否存在于 HTML 中 → 机械检查
- ❌ 检查 HTML 是否"好看" → 语义判断，交给 Agent

这符合 Dumb Tools 原则：工具检查"必须有什么"和"禁止有什么"，Agent 判断"好不好"。

## 9. 分权制衡（v1.1）

| 角色 | 职责 | 权力 | v1.1 强化 |
|---|---|---|---|
| 调研 Agent | 生产内容、写产物 | 生产权 | 必须填字段值，不能留空模板 |
| 审计 Agent | 独立审计、读者模拟 | 验证权 | 输出结构化重写指令 |
| 工具 | 记账、检查存在性+字段值+深度+依赖+HTML结构、构建 HTML | 记录权 | 检查更严格（9项必须结构），但仍机械 |

- 调研 Agent 不能自己批改自己的作业
- 审计 Agent 必须是独立会话，不知道调研过程
- 工具不假装 smart，只做 dumb 的存在性+字段值+深度+依赖+HTML结构检查

## 10. 美学规范（HTML 必读）

生成 HTML 前，**必须读** `09-HTML美学规范.md`。

核心要点：
- 背景 `#faf9f5`（米色，不是纯白）
- accent `#b85b44`（暖砖红）
- 字体 Lora + Inter + JetBrains Mono（Google Fonts CDN）
- h1 = 38px，hero-verdict = 30px，h2 = 26px
- 正文行高 1.75
- 必须有阅读进度条 + 侧栏 TOC
- 深度正文为主体（不是只有卡片）
- 表格用 Stripe Press 风格（无重边框）
- **aside.toc 禁止 overflow-y: auto**（v1.0 强制）
- **source-section div 必须正确闭合**（v1.0 强制）
- **必须有 9 项必须结构**（v1.1 强制，验证器检查）

**重要**：HTML 由 `build_html_v07.py` 工具生成，不由 Agent 手写。工具已内置美学规范，自动生成符合标准的 HTML。

## 11. 版本治理规则

1. **当前版本**：v1.1
2. **版本号标记**：每个文件头加 `<!-- ros-version: v1.2 | last-updated: YYYY-MM-DD | status: current -->`
3. **归档**：旧版本文件移到 `archive/v0.x/`，不删除
4. **archive/ 不作为规范**：Agent 不应参考 archive/ 里的文件
5. **CHANGELOG.md**：每次版本更新必须记录变更
6. **发布完整性**：每次发布必须同步更新
   - README.md
   - 00-使用说明.md（本文档）
   - CHANGELOG.md
   - 14-研究执行状态机.md
   - 所有模板文件的 ros-version 头
7. **工具与规范一致性**（v1.1 新增）：规范文档引用的工具必须存在于根目录，不能只存在于 archive/

## 12. 常见错误（Agent 必看）

### 错误 1：跳过入口文档

❌ 直接读 `09-可视化视图模型.md` 就开始写 HTML
✅ 必须先读 `00-使用说明.md`（本文档），理解完整流程

### 错误 2：用旧版美学

❌ 用 `#faf7f0` 背景、`#8b5a3c` accent、Georgia 字体
✅ 用 `#faf9f5` 背景、`#b85b44` accent、Lora 字体（见 `09-HTML美学规范.md`）

### 错误 3：只有卡片没有正文

❌ HTML 全是 summary_cards / object_cards，没有深度正文
✅ HTML 主体是深度正文（≥ 15000 字），卡片是辅助

### 错误 4：跳过反方审计

❌ 不做 red_team.md，或做了但没有触发降级
✅ 至少 4 次攻击，至少 1 次降级

### 错误 5：discarded.md 缺失

❌ 只有 candidates.md，没有 discarded.md
✅ discarded.md 是必产物——丢弃的源也要记录

### 错误 6：状态机不一致

❌ research_state.json 报告 "step 9 done" 但实际 final-report.md 不存在
✅ 状态必须准确反映实际完成情况

### 错误 7：subagent 写错路径

❌ subagent 把分析文件写到工作目录而不是项目 05-analysis/
✅ subagent 产出必须归位到标准目录结构

### 错误 8：跳过核心对象直采

❌ 直接从候选源进入多 Agent 分析，不做核心对象直采
✅ 步骤 6.5 必须完成，core_objects_fetch_log.md 必须有 URL≥3 + 对象≥3

### 错误 9：跳过独立审计

❌ 报告草稿写完直接进入 HTML 构建
✅ 步骤 9.5 必须由独立审计 Agent（不同会话）执行，5 问全 PASS

### 错误 10：工具越界做语义判断

❌ 在工具中硬编码产品名 / 用阈值决定 action
✅ 工具只做机械检查，语义判断交给 Agent

### 错误 11：手写 HTML 而不用工具（v1.1 新增）

❌ Agent 自己手写 HTML，绕过 build_html_v07.py 工具
✅ 步骤 13 必须用 `python build_html_v07.py "项目路径"` 工具驱动

**为什么这个错误严重**：
- 手写 HTML 无法保证美学规范一致性
- 手写 HTML 容易缺失必须结构（page-shell/aside.toc/vm-hero 等）
- 手写 HTML 和 final-report.md 容易不同步
- 工具已内置所有美学规范，自动生成合规 HTML

### 错误 12：规范引用已归档工具（v1.1 新增）

❌ 规范文档说"用 build_html_v07.py"但工具只在 archive/ 目录
✅ 工具必须在根目录可用，规范文档和实际状态必须一致

**v1.1 修复历史**：v1.0 归档了 build_html_v07.py 但没更新使用说明，导致 Agent 找不到工具被迫手写 HTML。v1.1 恢复工具到根目录。

## 15. 升级指南

如果要升级 Research OS 到新版本：

1. 在 `CHANGELOG.md` 记录变更
2. 更新所有文件的 `ros-version` 头
3. 旧文件移到 `archive/v0.x/`
4. 更新本文档（`00-使用说明.md`）
5. 更新 `README.md`
6. 跑 `validate_research_project.py` 确保不破坏现有项目
7. **Dumb Tools 合规自审**：检查工具是否有硬编码项目特定信息 / 阈值语义决策
8. **工具与规范一致性检查**（v1.1 新增）：规范文档引用的每个工具必须存在于根目录
9. **验证器覆盖度检查**（v1.1 新增）：规范要求的每个必须结构，验证器是否有对应检查
