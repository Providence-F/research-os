# Research OS 使用说明 v2.0

> **唯一入口**：Agent 拿到 Research OS 时，必须先读本文档。
> 如果本文档和其他文件冲突，以本文档为准。

---

## 1. Research OS 是什么

Research OS 是一个**深度调研工作流系统**。给定一个研究主题，它会引导你走完"任务定义 → 方向选择 → 候选源采集 → 证据矩阵 → 假设账本 → 核心对象直采 → 多 Agent 分析 → 行文思路规划 → 反方审计 → 独立审计 → 读者模拟 → 写-读-改闭环 → 最终报告 → HTML 可视化"的完整链路，产出一份有信任度保证的深度报告。

**设计哲学**：**Smart Agent. Dumb Tools.**
- 工具只做机械检查（存在性、字数、格式、字段值非空、必须结构正则匹配）
- 语义判断（好不好、要不要重写、质量高低）交给 Agent
- 工具不硬编码项目特定信息，不用阈值做语义决策

**核心原则**：内部文件服务可信度，最终报告服务读者。

## 4. 强制执行顺序（v2.0：23 步 + 12 个门禁）

Agent 必须按以下顺序执行，每步完成后跑 `validate_research_project.py` 检查。

**完整流程详见 [`14-研究执行状态机.md`](14-研究执行状态机.md)**。本节为摘要。

| 步骤 | 名称 | 驱动 | 产物 | 门禁 |
|---|---|---|---|---|
| 0 | 脚手架 | 工具 | 目录结构 | 无 |
| 1 | 路由 | Agent 显式选择 | research_mode 字段 | 无 |
| **1.2** | **意图探索** | **Agent** | **intent_doc.json + intent_tree + candidate_paths** | **gate_10** |
| **1.5** | **方向选择（边界追问）** | **Agent+用户** | **direction_selection.json** | **≥2边界问题+用户回答** |
| 2 | 任务卡 | Agent | task-card.md | 字段值非空 |
| 3 | 调研方案 | Agent | research-plan.md | 字段值非空 |
| 4 | 候选源 | Agent | candidates.md + discarded.md | 存在性 |
| 5 | 证据矩阵 | Agent | evidence_matrix.md | 存在性 |
| 6 | 假设账本 | Agent | hypothesis_ledger.json | 字段值非空 |
| **6.5** | **核心对象直采** | **Agent** | **core_objects_fetch_log.md** | **强制门禁** |
| 7 | 多 Agent 分析 | Agent | 4 个分析文件 | 依赖 6.5 + 5 |
| **7.5** | **行文思路规划** | **Agent** | **narrative-plan.md** | **强制门禁（v1.4新增）** |
| 8 | 反方审计 | Agent | red_team.md + insight_ledger.json | 字符数>=300 + gate_11 |
| 9 | 最终报告草稿 | Agent | final-report.md | URL>=5+数据点>=10+章节>=5 |
| **9.5** | **独立审计** | **审计 Agent** | **audit_report.md** | **5 问全 PASS** |
| **9.6** | **对抗式审核** | **subagent** | **adversarial_review.json** | **≥3攻击+对应回应** |
| 10 | 读者模拟 | 审计 Agent | reader_diagnosis.json + reader_feedback.md | 强制门禁 |
| **10.5** | **写-读-改闭环** | **工具+Agent** | **rewrite_instructions.json** | **通过或 max_iter** |
| 11 | 溯源清单 | Agent | trace-manifest.json | 存在性 + gate_12 |
| 12 | 视图模型 | Agent | view-model.json | 存在性 |
| 13 | HTML 构建 | **工具** | index.html | **门禁9：美学合规验证** |
| 14 | 验证 | 工具 | validation_report | 全部检查 |
| 15 | 发布 | 工具 | 桌面副本 | 无 |

### 12 个强制门禁（v2.0）

| 门禁 | 触发 | 要求 | 失败后果 |
|---|---|---|---|
| 1. 核心对象直采 | 步骤 7 前 | log 存在 + URL>=3 + 对象>=3 | 不能进入步骤 7 |
| 2. 独立审计 | 步骤 9 后 | audit_report.md 5 问全 PASS | 不能进入步骤 10 |
| 3. 读者模拟 | 步骤 9.6 后 | reader_diagnosis.json + reader_feedback.md 存在 | 不能进入步骤 10.5 |
| 4. 方向选择 | 步骤 2 前 | direction_selection.json + ≥2边界问题 + 用户回答 | 不能创建任务卡 |
| 5. 对抗式审核 | 步骤 9.5 后 | adversarial_review.json ≥3攻击+回应 | 不能进入读者模拟 |
| 6. 第一性原理 | 贯穿三层 | intent_doc + research-plan + final-report 三层检查 | 验证器报 FAIL |
| **7. 行文思路规划** | **步骤 8 前** | **narrative-plan.md 存在 + 关键词 + 元原则检查** | **不能进入步骤 8** |
| 8. 写-读-改闭环 | 步骤 10 后 | rewrite_instructions.json 生成 | 不能进入步骤 11 |
| 9. 美学合规验证 | 步骤 13 | index.html 通过禁止模式+必须结构+视觉量化检查 | 不能进入步骤 14 |
| **10. 意图树完整性** | **步骤 1.2 后** | **intent_tree L0-L4 分层 + candidate_paths + success_criteria** | **不能进入步骤 1.5** |
| **11. 洞察账本** | **步骤 8 后** | **insight_ledger.json verified>=3（R2）/>=5（R3）+ contrarian>=1 + evidence_ids>=2** | **不能进入步骤 9** |
| **12. 跨产物一致性** | **步骤 11 前** | **intent_tree.answer_pointer + insight.report_anchor + trace 链路 id 全部存在** | **不能进入步骤 12** |

  - `check_reader_simulation_v2`：outsider + layman 双读者独立阈值
  - `check_term_explanation_coverage_v2`：术语解释覆盖率（双读者视角）
  - `check_hard_constraints`：08-最终报告 H1-H12 硬约束清单
  - `check_cross_artifact_consistency`：intent_tree/insight/trace 跨产物 ID 一致性

## 10. 人工确认点（v1.4 变更）

### v1.4：仅保留方向选择

v1.4 删除了 step_2（任务卡）和 step_3（调研方案）的人工确认点，改为 Agent 自主完成 + 独立审计验证。

**唯一用户参与点**：step_1.5 方向选择——Agent 提出 2 个边界问题，用户回答。

其他步骤全部由 Agent 自主完成，由独立审计 Agent 验证。

### 防止"自己出题自己改答案"

1. **独立会话审计**：审计 Agent 必须是独立会话
2. **审计范围扩展**：独立审计不仅检查报告内容，还检查行文思路
3. **读者模拟对抗**：审计 Agent 扮演读者检查"能否看懂"
4. **对抗式审核**：subagent context 隔离

## 11. 美学规范（HTML 必读）

## 12. 版本治理规则

1. **当前版本**：v2.0
2. **版本号标记**：每个文件头加 `<!-- ros-version: v2.0 | last-updated: YYYY-MM-DD | status: current -->`
3. **归档**：旧版本文件移到 `archive/`
4. **CHANGELOG.md**：每次版本更新必须记录变更
5. **发布完整性**：每次发布必须同步更新 README / 00-使用说明 / CHANGELOG / 14-状态机 / 所有模板 ros-version 头

## 12.5 v2.0 核心机制（新增）

### 意图树（5 轮探索）

`intent_discovery.py v2.0` 把意图探索从 3 轮扩到 5 轮：

| 轮次 | 名称 | 产物 |
|---|---|---|
| R1 | 字面意图 | literal_intent |
| R2 | 差距扫描 | gap_checklist |
| R3 | 意图树 | intent_tree（L0 根 → L1 维度 → L2 子问题 → L3 假设 → L4 验证路径） |
| R4 | 候选路径 | candidate_paths（带剪枝机制） |
| R5 | 问题说明书 | intent_doc.json（含 success_criteria） |

支持 `revise_intent_tree`：在 R3 之后允许中途修订意图树。

### 洞察账本（insight_ledger.json）

`templates/25-洞察账本协议.md` 定义洞察的判定与流转：

- **洞察判定三条件**：反共识 / 可证伪 / 决策力
- **状态流转**：`draft` → `verified`（满足三条件）/ `downgraded`（降级为普通结论）/ `rejected`（证伪）
- **R2 阈值**：verified >= 3，其中 contrarian >= 1
- **R3 阈值**：verified >= 5，其中 contrarian >= 2
- 每个 verified 洞察必须有 `evidence_ids`（>=2 条证据）和 `report_anchor`（报告锚点）

### 叙事原型（6 种 archetype）

`templates/23-行文思路规划协议.md` v2.0 重构：用 6 种 archetype 替代单一行文思路模板。

| archetype | 适用主题 | 叙事主线 |
|---|---|---|
| learning_curve | 技术深度/学习路径 | 认知递进（入门→进阶→精通） |
| decision_forum | 决策支持/投资分析 | 多方观点→权衡→决策 |
| product_teardown | 产品拆解 | 由表及里（功能→机制→战略） |
| opportunity_map | 行业赛道/市场机会 | 机会扫描→评估→选择 |
| user_voice | 用户研究 | 真实声音→模式→洞察 |
| mixed_journey | 混合研究 | 多 archetype 编排 |

Agent 必须显式选择 archetype + 写 why_not（为什么不选其他），防止默认走 learning_curve。

### 双读者模拟（reader_simulation v2.0）

`reader_simulation.py v2.0` 从单读者扩为双读者：

| 读者 | 视角 | 阈值 |
|---|---|---|
| outsider | 行业外人：不懂术语，需要科普 | term_coverage >= 0.9 |
| layman | 完全外行：连行业背景都不懂 | term_coverage >= 1.0 + context_check |

两位读者独立评分，任一未达标则触发 rewrite。

## 13. 系统看板（v2.0）

### 定位

看板是**报告生产线的控制塔**，不是项目宣传页。回答三个问题：
1. 每个项目卡在 23 步流水线的哪个位置？
2. 哪个门禁在卡项目（瓶颈在哪）？
3. 哪些项目停滞、哪些未纳入状态机？

### 数据链（机械，无语义判断）

```
projects/ 真实产物 + research_state.json
        ↓  python ros.py dashboard  （即 scripts/sync_dashboard.py）
dashboard/src/data/{workflow,projects,versions,stats}.ts
        ↓  cd dashboard && npm run build
dashboard/dist/index.html（单文件）
```

- 工作流定义单一真相源：`workflow_def.py`（23 步 + 12 门禁 + 5 阶段）。
  改 `templates/14-研究执行状态机.md` 时必须同步改它。
- 项目状态判定是 Dumb 的：产物文件存在即步骤完成、门禁产物存在即门禁过。
- 无 research_state.json 的遗留项目：从产物存在性机械推断，标「未纳入」。

### 怎么看

- **圆点** = 项目，落在它当前所处的步骤上；**颜色** = 健康度
  （绿=已交付 / 砖红=门禁卡住 / 灰=停滞 14 天 / 空心=未纳入）。
- **菱形** = 门禁，项目当前位置之前首个未过门禁即卡点。
- **堆积处即瓶颈**：同一步骤上堆多个项目，说明该步骤是系统性堵点。
- 点击项目 → 抽屉显示 23 步逐步状态 + 12 门禁逐个过/未过。

### 线上看板

- 地址：https://providence-f.github.io/research-os/
- 部署：push 到 master 且改动涉及 `dashboard/**`、`scripts/sync_dashboard.py` 或
  `CHANGELOG.md` 时，GitHub Actions 自动 npm build 并发布（`.github/workflows/deploy-dashboard.yml`）。
- **推 master 前必须先跑 `python ros.py dashboard`**，否则线上数据是旧的。
