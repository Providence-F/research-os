# Research OS v0.1 使用说明

这是通用深度调研工作流的第一版模板库。

路径：`E:\obsidian\AI革命生存指南\09-收件箱\Research OS 深度调研工作流\04-模板库`

---

## 第一性原理：内部可信度 vs 读者交付

Research OS 有两层产物，不能混在一起。

### 1. 内部工作区

服务对象：Agent、研究者、审计者。

包括：任务卡、调研方案、候选源、被丢弃来源、证据矩阵、冲突信息、反方审计。

作用：保证过程可追踪、结论可溯源、错误可审计。

这些文件可以很程序化，可以有 evidence_id、conclusion_id、证据等级、状态字段。

### 2. 最终交付层

服务对象：真正的读者。

必须产出两份：

1. `07-output/final-report.md`：一篇完整、连贯、可读的 MD 调研报告。用于知识库存储，也便于 Agent 后续读取。
2. `08-html/index.html`：从读者版 MD 报告生成的黑白极简交互 HTML。用于阅读、展示、分享。

最终交付不能把内部证据数据库直接拼贴出来。

读者版报告必须：

- 先讲实质内容：这是什么、判断是什么、为什么、对我有什么用。
- 再讲分析：产品机制、用户场景、差异化、商业模式、风险、行动建议。
- 最后才放证据、溯源、反方审计、来源清单。
- evidence_id、conclusion_id 可以保留在附录，不要淹没主体。
- HTML 不是所有工作区文件的拼贴，而是最终报告的可视化阅读版。

一句话：**内部文件服务可信度，最终报告服务读者。**

## Kimi 启发的运行原则

1. **深度调研不是搜索能力，是信息筛选能力。** 先广撒网，再狠淘汰。
2. **必须记录丢弃了什么，为什么丢弃。** `02-sources/discarded.md` 是必产物。
3. **证据矩阵不是附录，是中间数据库。** 每条证据有 evidence_id，结论通过 ID 引用。
4. **冲突信息显性化。** 冲突进 `conflicts.md`，不被"取平均"抹平。
5. **结论必须可溯源。** 每条结论有 `supported_by`，没有证据的结论标"待验证"或删除。
6. **Agent 数量不等于信息质量。** 信息稀缺时收敛深度，不强行写完整商业分析。

## 使用顺序

### 1. 先填调研任务卡

使用：`01-调研任务卡.md`

目的：先搞清楚这次调研服务什么决策。

不要跳过。如果这一步不清楚，后面搜得越多越乱。

### 2. 再写调研方案

使用：`02-调研方案.md`

目的：确定调研类型、深度档位、平台矩阵、Agent 分工、子问题矩阵、停止条件、验收标准。

这一步是唯一建议人工确认的地方。确认后再执行。

### 3. 建证据矩阵

使用：`03-证据矩阵.md`

目的：把事实、来源、证据等级、冲突信息、结论溯源放进同一个表。

核心规则：

> 每条信息都要知道自己能支撑什么结论。每条结论都要知道被哪些证据支撑。

### 4. 如果涉及平台搜索，用平台审计矩阵

使用：`04-平台审计矩阵.md`

尤其适合：公司调研、JD 调研、招聘平台调研、产品官网 / 社媒 / 应用商店对照。

不要把"搜到"当"验证过"。

### 5. 如果涉及用户需求，用用户原声库

使用：`05-用户原声库.md`

核心规则：用户原话必须保留，不要先翻译成 AI 总结。

### 6. 如果涉及 JD，用逐句拆解模板

使用：`06-JD逐句拆解.md`

硬规则：完整 JD 才能逐字逐句拆。列表摘要只能作为岗位信号。

### 7. R1 以上必须做反方审计

使用：`07-反方审计.md`

如果反方审计没有导致任何结论降级，说明审计不够用力。

R2+ 必须做多 Agent 角色包 + HTML 可视化。

### 8. 最后写最终报告

使用：`08-最终报告.md`

报告不是按"我搜了什么"来写。而是按"读者怎么决策"来写。

必须包含：信息淘汰说明、结论溯源表、结论置信度。

## 深度档位选择

| 档位 | 用途 | 输出 | 反方审计 | HTML |
|---|---|---|---|---|
| R0 | 快速判断是否值得继续 | 一页判断 | 可跳过 | 不要求 |
| R1 | 判断是否行动 | 标准报告 + 证据矩阵 | 必做 | 不要求 |
| R2 | 形成高质量判断 / 作品集 / 公开报告 | 完整报告 + HTML + 反方审计 | 必做 | 必做 |
| R3 | 长期复用 | 数据库 / 持续更新报告 | 必做 | 必做 |

## 什么时候接 Dify

现在不要急着接。v0.1 目标是把流程跑稳。

当以下条件满足，再接 Dify：

- 已经用模板跑过 2-3 个真实项目
- 调研任务卡稳定
- 证据矩阵字段稳定
- 反方审计模板稳定
- HTML 输出结构稳定
- 已经知道哪些步骤需要人工确认

Dify 适合做：表单入口、需求挖掘、调研类型分类、深度档位判断、调研方案生成、人工确认、调用 Claude Code / Agent Loop。

Dify 不适合做：长时间浏览器自动化、本地文件读写、Playwright 登录态操作、HTML 调试、GitHub Pages 部署。

一句话：

**Dify 做流程中控，Claude Code 做执行引擎，Obsidian 做长期记忆。**
