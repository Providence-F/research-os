# 可视化视图模型模板

> `final-report.md` 负责完整论证，`view-model.json` 负责 HTML 怎么被读者快速理解。不要把正文复制进视图模型，只抽出可视化所需的数据结构。

## 1. 基本原则

- HTML 必须仍然保留完整正文。
- 第一屏必须先降低认知负担：判定、摘要卡片、关键对象、策略或对比。
- R2/R3 且非 `narrative_report` 的项目必须生成 `07-output/view-model.json`。
- 视图模型只存结构化展示数据，不替代证据矩阵和最终报告。

## 2.5 字段写作指引（面向读者，不是面向开发者）

> 以下字段会直接展示在 HTML 报告上，读者会看到。不要写实现细节。

| 字段 | 写什么 | 不要写什么 |
|------|--------|-----------|
| `hero.verdict` | 一句话核心判断，读者看完就知道结论 | 不要写 step 编号、文件路径、schema 名词 |
| `hero.summary` | 2-3 句话解释判断的依据，面向非技术读者 | 不要写"插在 X 和 Y 之间""5 个生成器构成 Z"等实现细节 |
| `hero.meta` | 调研深度、日期、证据数量等元信息 | 不要写内部模块名 |
| `summary_cards[].content` | 每张卡片一个关键结论 + 证据简述 | 不要复制报告段落 |
| `object_cards[].summary` | 对象的一句话描述，读者能看懂 | 不要写技术规格参数清单 |

**检验标准**：把 hero.verdict 和 hero.summary 给一个非技术人员看，他能看懂在说什么。如果出现 step_、.json、view-model 这类词，就是写错了。

## 3. 按研究模式填写

### thinking_decision / career_strategy

必须有：

- `hero.verdict`：当前判断。
- `summary_cards`：3-6 张关键结论卡。
- `object_cards`：候选项、导师、项目、路径。
- `strategy_tabs`：首选 / 备选 / 保底 / 禁区。
- `comparison_matrix`：横向比较成本、收益、风险、可执行性。

### product_teardown

必须有：

- 产品机制卡片。
- 用户路径或核心 workflow。
- 风险 / 待验证卡片。
- 和竞品或替代方案的比较矩阵。

### opportunity_map

必须有：

- 排名卡片或对象卡片。
- 筛选表格。
- 详情弹窗字段：基础事实、匹配理由、风险、下一步动作、来源。

### user_voice

必须有：

- 用户原声主题卡片。
- 高频需求 / 痛点 / 场景筛选。
- 证据等级和代表性限制。

### narrative_report（叙事报告）

visual_modules 只需：`hero`、`full_report`、`appendix_fold`。

**不要创建** object_cards、strategy_tabs、comparison_matrix、filterable_table——
这些是 product_teardown/opportunity_map 用的模块，叙事报告不需要。
如果创建了空字段，Agent 会被引导去填不需要的数据。

## 4. 验收

- 第一屏能看懂结论，不需要先滚完整正文。
- 对象拆解不能只藏在长段落里。
- 至少出现一种交互：卡片、Tab、筛选、弹窗、矩阵。
- 附录和审计默认折叠。
