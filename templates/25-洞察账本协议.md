# 洞察账本协议（v2.0 新增）

> v2.0 核心新增。解决"报告=资料汇编，信息量有但洞察没有"的系统性问题。
> 此协议定义什么是洞察（insight），并要求每条洞察在 `05-analysis/insight_ledger.json` 登记、可验证、可溯源。
> 洞察的候选产生于 step_6 之后，verified 判定完成于 step_9.6 之前，落点检查发生在 step_9 与 step_11。

---

## 1. 为什么需要这个协议

v1.x 的问题是：证据矩阵保证"事实有出处"，第一性原理保证"有本质拆解"，但没有任何机制保证"报告里有超越资料的判断"。

结果：
- 报告把公开信息组织得很整齐，读者读完说"都是我知道的"
- "洞察"是语义质量，靠 Agent 自觉，系统无法检查"有没有、真不真"
- 正确的废话（"AI 发展很快""市场竞争激烈"）冒充结论，不可追责

v2.0 的解决思路：
1. **定义判定标准**：先讲清楚什么是洞察、什么是正确的废话（本节第 2 条）
2. **结构要求**：每条洞察必须在 insight_ledger.json 登记，字段机器可验证（可机械检查"有没有"）
3. **对抗验证**：红队和对抗审核攻击每条洞察的 falsifier 与 novelty_check（可检查"真不真"）
4. **数量硬规则**：verified 洞察的数量与分布是 step_9 的前置门禁（可检查"够不够"）

---

## 2. 什么是洞察（判定标准）

**洞察 = 非显而易见的因果判断或结构判断。** 一条陈述必须同时满足以下三条，才允许登记为洞察：

| 判定 | 含义 | 反例 |
|---|---|---|
| (a) 反常识或超越公开共识 | 任何人在谷歌/百度第一页就能找到的判断，不是洞察 | "远程办公越来越流行" |
| (b) 可证伪 | 存在一种可想象的观察，能推翻它 | "企业文化很重要"（什么观察都推翻不了） |
| (c) 对读者决策有改变力 | 读者知道它之后会做出不同选择 | "该公司成立于 2021 年"（知道前后行为不变） |

**对照定义：正确的废话（platitude）**——满足以下任意一条即判定为废话，禁止作为洞察登记，禁止作为报告段落结论：

- 不可证伪：不存在能推翻它的观察（"团队是成功的关键"）
- 无决策含量：读者知道前后行动不变（"市场规模很大"）
- 纯描述：只陈述事实，不含因果或结构判断（"该产品有 12 个功能"）

**判定示例**：
- ✗ "AI Agent 赛道竞争激烈" → 谷歌第一页共识，不可证伪，无决策含量。废话。
- ✗ "该公司增长很快" → 纯描述。废话。
- ✓ "该公司的留存率来自'默认勾选年费'的定价设计而非产品力——若取消默认勾选，留存会跌至行业均值以下" → 超越公开叙事（contrarian），可证伪（观察取消勾选后的留存数据），改变决策（求职者/投资者应调低对其产品力的评估）。洞察。

## 3. 洞察账本 JSON 结构

产物：`05-analysis/insight_ledger.json`

完整示例（字段全部机器可验证）：

```json
{
  "insights": [
    {
      "id": "I1",
      "claim": "该公司的留存率来自定价设计而非产品力",
      "type": "contrarian",
      "evidence_ids": ["E003", "E007"],
      "falsifier": "取消默认勾选年费的竞品对比实验中，留存仍高于行业均值",
      "confidence": "medium",
      "novelty_check": "公开叙事将其增长归因于产品力（36氪、官网PR）；本判断归因于定价机制，未见公开报道",
      "decision_impact": "读者（求职者）应把'产品力锻炼'权重调低，把'增长工程文化'权重调高",
      "report_anchor": "§5 差异化与竞争位置",
      "status": "verified"
    },
    {
      "id": "I2",
      "claim": "该技术的性能优势只在数据规模超过阈值后显现",
      "type": "causal",
      "evidence_ids": ["E012", "E015"],
      "falsifier": "在小规模数据集上也观测到稳定优势",
      "confidence": "high",
      "novelty_check": "官方文档宣称全场景优势；阈值效应只在论文附录出现，未进入科普叙事",
      "decision_impact": "零基础读者应明白：小团队场景下选型不必追此技术",
      "report_anchor": "§3 核心机制",
      "status": "verified"
    },
    {
      "id": "I3",
      "claim": "创始人的上一份创业经历决定了本公司的渠道基因",
      "type": "structural",
      "evidence_ids": ["E021"],
      "falsifier": "渠道负责人访谈显示渠道体系与前公司无人员/方法继承",
      "confidence": "low",
      "novelty_check": "未检索到公开分析建立此关联",
      "decision_impact": "（暂不影响主结论）",
      "report_anchor": "",
      "status": "rejected"
    }
  ]
}
```

字段约束（机械可验证）：

- `id`：格式 `I\d+`，账本内唯一
- `type`：枚举 `causal | structural | contrarian`
  - causal：因果判断（X 导致 Y）
  - structural：结构判断（X 的本质结构是……）
  - contrarian：与主流叙事相反的判断
- `evidence_ids`：数组，元素必须能在 `evidence_matrix.md` 中找到对应 evidence_id
- `falsifier`：非空字符串，描述"什么观察会推翻它"
- `confidence`：枚举 `high | medium | low`
- `novelty_check`：非空字符串，说明与公开共识的差异
- `decision_impact`：非空字符串，说明读者知道后会改变什么行动
- `report_anchor`：verified 条目必填，指向 final-report.md 的章节标题
- `status`：枚举 `draft | verified | downgraded | rejected`

## 4. 数量与分布硬规则

| 规则 | 内容 | 机械检查 |
|---|---|---|
| R4.1 | R2 深度报告 ≥3 条 verified 洞察；R3 ≥5 条（R0/R1 不强制） | 按 task-card.md 的深度档位计数 status=verified 条目 |
| R4.2 | verified 洞察中至少 1 条 type=contrarian（倒逼对抗思考） | 过滤 verified 后检查 type 枚举存在性 |
| R4.3 | 每条 verified 洞察必须有 ≥2 个 evidence_ids，且对应证据在证据矩阵中"来源独立性"不全是"同源传抄" | 数组长度 + evidence_matrix.md 字段回查 |
| R4.4 | status 流转：`draft` →（step_8 红队 / step_9.6 对抗审核后）→ `verified` 或 `downgraded` 或 `rejected`；不允许 draft 直接进入报告 | step_9 门禁：status=draft 条目数 = 0 |
| R4.5 | **step_9（报告草稿）开始前，verified 洞察禁止为 0 条**；且必须满足 R4.1 的数量要求 | step_9 前置门禁：verified 计数 ≥ 档位下限 |
| R4.6 | rejected / downgraded 条目的 report_anchor 必须为空字符串 | 字段值检查 |

## 5. 与现有步骤的绑定

| 步骤 | 绑定 | 说明 |
|---|---|---|
| step_6 假设账本 | 洞察的候选池 | hypothesis_ledger.json 中 status=confirmed 的假设是洞察的第一候选来源；登记为洞察时必须补齐 falsifier / novelty_check / decision_impact 三字段（假设账本不要求这三项） |
| step_7.5 行文思路规划 | 洞察的落点预排 | narrative-plan.md 的章节骨架应为每条 draft 洞察预留落点章节 |
| step_8 红队 | 攻击 falsifier | red_team.md 必须对每条 draft 洞察执行"能否找到推翻它的观察"攻击；攻击存活的条目才允许进入 verified 候选 |
| step_9 报告草稿 | 洞察落点 | 每条 verified 洞察必须有 report_anchor，且该章节标题在 final-report.md 中存在（门禁，对应 08 的 H6） |
| step_9.6 对抗审核 | 核验 novelty_check | adversarial_review.json 必须含 type=insight_novelty 的攻击：subagent 逐条判断"这是公开共识吗"；被判定为共识的条目降级为 downgraded |
| step_11 溯源清单 | insight→evidence 链路 | trace-manifest.json 必须为每条 verified 洞察建立 洞察→evidence_ids→来源URL 的完整链路 |

## 6. 反僵化条款

- 允许 rejected 洞察留在账本里，作为探索痕迹——它证明系统尝试过这条路。禁止为了"账本好看"删除 rejected 条目。
- 报告不得引用 rejected / downgraded 的洞察作为结论（R4.6 机械保证：这两条状态的 report_anchor 必须为空）。
- downgraded 条目允许以"事实陈述"身份留在报告中（降级为普通信息点），但不得以"洞察"身份出现在结论性位置。
- 洞察数量不设上限。硬规则只保下限，不鼓励凑数——step_9.6 的 novelty 核验会把凑数条目打回。

## 7. 验证规则

### 机械检查（Dumb Tools）

- `05-analysis/insight_ledger.json` 存在且为合法 JSON，顶层含 `insights` 数组
- 每条洞察含第 3 节全部 10 个字段；枚举字段值合法（id 格式 / type / confidence / status）
- evidence_ids 元素在 `evidence_matrix.md` 中存在对应 evidence_id
- R4.1 数量下限、R4.2 contrarian 存在性、R4.3 证据数 ≥2、R4.6 report_anchor 空值约束
- step_9 门禁：无 status=draft 条目，且 verified 计数 ≥ 档位下限
- adversarial_review.json 含 type=insight_novelty 的攻击条目

### 语义检查（审计 Agent / 对抗 subagent）

- 每条 verified 洞察是否真的满足第 2 节三条判定（反共识 / 可证伪 / 有决策力）
- falsifier 是否是"可想象的观察"而非同义反复
- novelty_check 声称的"公开共识"是否属实（抽样检索验证）

## 8. 与其他协议的关系

- **04-假设账本**：假设是洞察的候选池；洞察 = 通过对抗验证、补齐三字段的假设
- **21-对抗式审核协议**：新增 insight_novelty 攻击类型，与 first_principles 再分测试并列
- **22-第一性原理拆解协议**：第一性原理回答"为什么会发生"，洞察回答"所以呢、怎么办"；原理是洞察的论据，不是洞察本身
- **23-行文思路规划协议**：叙事原型决定洞察的呈现顺序；每个原型的"关键张力"通常应由 contrarian 洞察承担
- **08-最终报告**：H6（洞察落点）与 H7（禁止正确的废话）是本协议在报告层的执行端
- **15-结论溯源清单**：step_11 为每条 verified 洞察建立完整溯源链路
