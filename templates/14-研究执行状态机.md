# 14-研究执行状态机 v0.5

Research OS 的核心不是多一个 CLI，而是把一次研究从"写报告"改成**可检查、可溯源、可迭代**的状态推进。

## 1. 状态顺序（v0.5 完整 15 步）

v0.5 从 v0.4 的 12 步线性流程升级为 15 步，**加入了写-读-改闭环**（step 10），不再是纯线性：

```text
step 0  scaffold       -> 创建项目目录和全部模板
step 1  route           -> 路由 + 意图探索
step 2  task_card       -> 填任务卡 🛑（人工确认）
step 3  research_plan   -> 调研方案 🛑（人工确认）
step 4  candidates      -> 候选池 + 丢弃源
step 5  evidence        -> 证据矩阵
step 6  hypothesize     -> 假设账本 + 冲突
step 7  analysis        -> 多 Agent 分析
step 8  red_team        -> 反方审计（必须触发至少 1 次降级）
step 9  report_draft    -> 最终报告草稿
step 10 reader_simulation -> 读者模拟 + 报告重写（写-读-改闭环）⭐ v0.5 新增
step 11 trace_manifest  -> 结论溯源清单
step 12 view_model      -> 视图模型 JSON
step 13 html_build      -> HTML 构建 🛑（美学合规确认）
step 14 validate        -> 强制验证
step 15 publish         -> 发布到桌面
```

**v0.5 vs v0.4 关键变化**：
- 加入 `step 0 scaffold`（v0.4 没有显式的脚手架步骤）
- 加入 `step 7 analysis`（v0.4 没有显式的多 Agent 分析步骤）
- 加入 `step 10 reader_simulation`（v0.10 引入的写-读-改闭环，v0.5 固化）
- 加入 `step 15 publish`（v0.4 没有显式的发布步骤）
- 加入 3 个人工确认点（v0.4 没有显式标注）

## 2. 下一步动作判定

`research_status.py` 不是简单检查哪个文件缺失，而是**先检查研究内核是否成立**：

1. 没有 `research_state.json`：先修路由状态。
2. 没有任务卡：先填 `task-card.md`，等待人工确认。
3. 没有调研方案：先运行 `research_planner.py`，等待人工确认。
4. 候选池为空，或没有显式淘汰任何候选（`discarded.md` 缺失或为空）：继续做候选池。
5. 假设少于 3 条，或没有任何假设被修正 / 降级 / 拒绝：继续更新假设账本。
6. `conflicts.md` 缺失：继续记录冲突。
7. final-report 已有但 trace-manifest 缺失或为空：先写结论溯源。
8. final-report 已有但未跑 reader_simulation：先跑写-读-改闭环（step 10）。
9. Validator 有 FAIL：先修验证失败。
10. 研究内核和结论溯源通过后，才补 view-model / HTML。
11. HTML 生成后必须检查美学合规（见 `09-HTML美学规范.md`）。

这个顺序防止系统出现三类错误：

- 候选池和假设账本还没完成，却因为缺 HTML 就提示构建页面；
- 报告写得很顺，但强结论没有回到证据和假设账本；
- **v0.5 新增**：报告写完没跑读者模拟就生成 HTML，导致读者看不懂。

## 3. 写-读-改闭环（v0.5 核心创新）

**这是 v0.10 引入、v0.5 固化的关键创新**。`step 10` 不是可选的：

```text
step 9  final-report.md（草稿）
   ↓
step 10 reader_simulation.py
   ↓ 模拟读者阅读，找出：
   ↓   - 看不懂的术语（没加括号解释）
   ↓   - 逻辑跳跃（缺少推导步骤）
   ↓   - 结论没有证据支撑
   ↓   - 章节断裂
   ↓
   ↓ final_report_writer.py
   ↓ 根据读者反馈重写报告
   ↓
step 10 final-report.md（重写后）
```

**为什么必须做**：写报告的人和读报告的人视角不同。作者觉得"已经讲清楚了"的地方，读者可能完全看不懂。`reader_simulation.py` 模拟一个非技术背景读者，找出所有"看不懂"的地方，然后 `final_report_writer.py` 重写。

**可能迭代多轮**：如果第一轮重写后读者模拟仍有问题，继续迭代，直到读者模拟通过。

## 4. Planner 的边界

`research_planner.py` 只生成初始研究计划：

- 子问题矩阵
- 初始假设
- 候选池占位
- 假设账本占位
- `research_state.json.next_required_action`

它**不替代研究者**。真实研究必须继续完成：

- 候选来源召回
- 显式淘汰
- 证据矩阵
- 假设修正
- 反方审计
- 读者版报告
- 结论溯源清单

## 5. Run Step 的边界

`research_run_step.py` 只自动执行低风险动作：

- `run_research_planner`
- `build_html`

以下动作只输出说明，不自动编造：

- `fill_candidate_pool`
- `fill_evidence_matrix`
- `update_hypothesis_ledger`
- `run_red_team_review`
- `write_reader_first_report`
- `write_trace_manifest`
- `write_view_model`
- **v0.5 新增**：`run_reader_simulation`（必须人工触发，因为可能迭代多轮）

自动化不能替代判断。

## 6. v0.5 的质量底线

R2/R3 项目至少满足：

### 6.1 候选池
- 有 `candidates.md`（v0.5：不只是 `candidate_pool.json`）
- 候选池不能为空
- 至少有一个候选被丢弃
- 有 `discarded.md`（v0.5 新增：必产物）
- 被丢弃候选必须写 `discard_reason`

### 6.2 假设账本
- 有 `hypothesis_ledger.json`
- 至少 3 条假设
- 至少 1 条假设被修正、降级或拒绝
- 假设必须链接 supporting 或 contradicting evidence
- 有 `conflicts.md`（v0.5 新增：必产物）

### 6.3 反方审计
- 至少 4 次攻击
- 至少 1 次降级（confirmed → partial/rejected）
- 降级必须记录在 `hypothesis_ledger.json`

### 6.4 最终报告
- 深度正文为主体（≥ 15000 字）
- 不是只有卡片
- 所有术语括号解释
- 第一性原理推导

### 6.5 溯源
- 有 `trace-manifest.json`
- strong claim 必须链接 hypothesis
- strong claim 必须链接 evidence，或写清 limitations

### 6.6 视图模型
- 非 narrative 报告必须有 view model 和视觉模块
- schema_version = `research-os-view-model-v0.5`

### 6.7 HTML（v0.5 增强）
- 必须保留完整正文
- 必须遵循 `09-HTML美学规范.md`
- 背景 `#faf9f5`，accent `#b85b44`
- 字体 Lora + Inter + JetBrains Mono
- h1 = 38px，hero-verdict = 30px，h2 = 26px
- 必须有阅读进度条 + 侧栏 TOC

### 6.8 版本一致性（v0.5 新增）
- 所有文件 `schema_version` 必须含 `v0.5`
- 不允许混用 v0.1/v0.3/v0.4 的 schema

## 7. 使用命令

```bash
# v0.5 CLI 命令
python ros.py new "项目名" --type product --depth R2 --html
python ros.py plan "项目路径"
python ros.py status "项目路径"
python ros.py run "项目路径"
python ros.py validate "项目路径"
python ros.py build --project "项目路径"
python ros.py rewrite "项目路径"  # v0.5 新增：写-读-改闭环
python ros.py discover "项目路径"
python ros.py goal "项目路径"
python ros.py iterate "项目路径"
python ros.py confirm "项目路径"
python ros.py dashboard "项目路径"
```

命令只是给 agent 和本地自动化调用的薄控制层，不是最终产品形态。最终交付仍是 Obsidian 项目文件、Markdown 报告和 HTML 页面。

## 8. 版本治理

| 版本 | 状态机步数 | 关键变化 |
|---|---|---|
| v0.4 | 12 步线性 | 候选池→证据→假设→红队→报告→溯源→视图→HTML |
| **v0.5** | **15 步 + 写-读-改闭环** | 加入 scaffold / analysis / reader_simulation / publish 步骤，加 3 个人工确认点 |
