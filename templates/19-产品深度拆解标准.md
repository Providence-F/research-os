# 产品深度拆解标准（v1.3 补全）

> v1.2 时此文件是 placeholder，导致"功能模块级深度"无定义。
> v1.3 补全：定义"概述级/功能模块级/架构级"的判定标准和必填字段。

---

## 1. 三级深度定义

### 概述级（不达标）

特征：
- 只描述"产品是做什么的"
- 无功能模块拆解
- 无技术架构信息
- 无定价细节

示例（不达标）：
> MiniMax 是一家 AI 公司，提供对话 AI 产品，有海外业务。

### 功能模块级（达标）

特征：
- 拆解到 3+ 个功能模块
- 每个模块有明确的功能描述
- 有定价体系（不是"有免费版"这种概述）
- 有技术架构的关键信息（模型类型/部署方式/API 接入）

示例（达标）：
> MiniMax 的产品矩阵包含：
> 1. Talkie（toC 角色扮演）：海外版星野，2.36亿用户，73%海外收入
> 2. 海螺 AI（toC 对话）：国内版对话助手
> 3. API 平台（toB）：提供 abab 系列模型 API
> 定价：API 按 Token 计费，abab6.5s ¥1/百万Token；Talkie 订阅制 $9.99/月
> 技术架构：自研 MoE 架构，私有部署 + API 双模式

### 架构级（超出标准）

特征：
- 在功能模块级基础上，拆解到技术实现细节
- 有性能指标（延迟/吞吐/准确率）
- 有竞品技术对比

---

## 2. 必填字段（功能模块级）

每个核心对象必须提取以下字段：

| 字段 | 说明 | 必填 |
|---|---|---|
| `product_positioning` | 产品定位（一句话） | ✅ |
| `feature_matrix` | 功能矩阵（3+ 模块） | ✅ |
| `tech_architecture` | 技术架构（模型/部署/API） | ✅ |
| `pricing` | 定价体系（具体价格，非概述） | ✅ |
| `customer_cases` | 客户案例或用户数据 | ✅ |
| `operational_metrics` | 运营指标（DAU/MAU/收入等） | ⚠️ 如公开则必填 |
| `competitive_position` | 竞争位置 | ⚠️ 如有则填 |

---

## 3. 验证器检查规则

验证器检查 `04-captures/core_objects_fetch_log.md`：
- 每个核心对象必须包含上述 5 个必填字段
- 字段值不能是"无"/"未知"/"待补充"（这些标记说明未真正直采）
- 功能矩阵必须列出 ≥3 个模块
