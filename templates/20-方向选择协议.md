# 步骤 1.5：方向选择协议（边界追问）

> v1.4 升级：从"≥2方向选择"改为"2个边界追问"，更轻量、更聚焦。
> v1.3 原版：Agent 给出 2-3 个完整方向，用户选择。
> v1.4 改版：Agent 给出 2 个边界问题，用户回答。聚焦用户意图的模糊处。
> 适用范围：R2/R3 深度调研强制，R0/R1 可选。

---

## 1. 为什么需要这一步

深度调研最大的浪费不是"做错了"，而是"方向错了却做完了"。

v1.3 的方向选择是"让用户选方向"——Agent 给出 2-3 个完整方向，用户选择。这比完整方案确认便宜，但仍有问题：
1. **方向设计成本高**：Agent 需要设计 2-3 个完整方向，每个含核心问题/研究路径/预期产出
2. **用户选择成本高**：用户需要理解 2-3 个方向的差异才能选择

v1.4 改为边界追问——Agent 只问 2 个边界问题：
1. **更轻量**：Agent 不需要设计完整方向，只需识别用户意图的模糊处
2. **更聚焦**：问的不是"你要什么"（用户已说过），而是"你不要什么"和"范围到哪"
3. **更早纠偏**：用户回答 2 个问题就能消除歧义

---

## 2. 执行流程

### 步骤 1：Agent 识别意图模糊点

Agent 读取 intent_doc.json，识别用户原始指令中容易遗漏的边界：

常见边界类型：
- **范围边界**：是否需要对比海外竞品？是否需要深入到代码级？
- **深度边界**：产品功能层面足够，还是需要技术架构分析？
- **时间边界**：只看当前状态，还是需要历史演变？
- **决策边界**：只做认知，还是需要明确投递建议？

### 步骤 2：Agent 提出 2 个边界问题

Agent 向用户提出 2 个边界澄清问题。

要求：
- 只问 2 个问题（不是 2-3 个完整方向）
- 每个问题给出默认选项，用户可以快速回答
- 问题聚焦"边界"（范围/深度/时间/决策），不是"方向"（你要走哪条路）

示例（Manus 调研）：
- 问题1（范围边界）："是否需要对比 Manus 与海外竞品（如 Devin/AutoGPT）的技术差异？" 默认：否，聚焦 Manus 本身
- 问题2（深度边界）："是否需要深入到代码级技术栈分析，还是产品功能层面足够？" 默认：产品功能+技术栈概述

### 步骤 3：用户回答

用户回答方式：
- 直接选默认（最低成本，1秒）
- 修正默认（中成本，10秒）
- 自定义回答（高成本，30秒）

### 步骤 4：Agent 基于回答创建任务卡

Agent 基于用户回答的边界，创建任务卡。

## 3. 产物文件

产物：`00-task/direction_selection.json`

格式：

```json
{
  "schema_version": "research-os-direction-v1.1",
  "project_name": "项目名",
  "created_at": "2026-07-12",
  "method": "boundary_clarification",
  "boundary_questions": [
    {
      "id": "Q1",
      "type": "scope|depth|time|decision",
      "question": "边界问题",
      "default_answer": "默认答案",
      "user_answer": "用户回答",
      "answered_at": "2026-07-12"
    },
    {
      "id": "Q2",
      "type": "scope|depth|time|decision",
      "question": "边界问题",
      "default_answer": "默认答案",
      "user_answer": "用户回答",
      "answered_at": "2026-07-12"
    }
  ],
  "status": "direction_confirmed"
}
```

---

## 4. 验证规则

- 产物文件必须存在：`00-task/direction_selection.json`
- `boundary_questions` 必须有 ≥2 个问题
- 每个问题必须有 `user_answer` 非空
- `status` 必须为 `direction_confirmed`
- R2/R3 深度调研时，任务卡创建前必须存在此产物

---

## 5. 与其他步骤的关系

- 前驱：步骤 1（意图识别）
- 后继：步骤 2（任务卡）
- 没有此产物（R2/R3），步骤 2 不能开始
- 验证脚本检查此文件存在 + 字段完整性

---

## 6. v1.3 到 v1.4 的迁移

v1.3 的 `directions_proposed` + `user_selection` 字段仍向后兼容。
v1.4 新增 `method` 字段（值为 `boundary_clarification`）和 `boundary_questions` 字段。
验证器同时支持两种格式。

---

## 7. 成本控制

- 边界追问只增加 1 轮用户对话（2个问题）
- 比完整方向选择更轻量
- 对 R0/R1 不强制（成本低，错了重来也快）
- 对 R2/R3 强制（成本高，方向错误代价大）
