# 15-结论溯源清单

Research OS v0.4 增加 `trace-manifest.json`，用来约束最终报告里的强结论。

核心原则：

> final-report 可以面向读者，但强结论必须能回到 hypothesis_ledger 和 evidence_matrix。

## 1. 文件位置

```text
07-output/trace-manifest.json
```

## 2. Schema

```json
{
  "schema_version": "research-os-trace-manifest-v0.4",
  "project_name": "",
  "claims": [
    {
      "id": "C001",
      "claim": "",
      "claim_strength": "strong / medium / weak",
      "report_section": "",
      "hypothesis_ids": ["H001"],
      "evidence_ids": ["E001"],
      "confidence": "high / medium / low",
      "limitations": ""
    }
  ]
}
```

## 3. 什么必须 trace

必须进入 trace-manifest：

- 最终建议；
- 排名、优先级、投递判断；
- “值得 / 不值得 / 应该 / 不应该”这类决策判断；
- 从事实推出的策略判断；
- 被 red team 降级过的结论；
- HTML 第一屏 hero 或 summary card 中出现的判断。

不强制进入 trace-manifest：

- 纯背景描述；
- 已在证据矩阵中直接列出的低风险事实；
- 附录里的过程说明；
- 明确标注为待验证的问题。

## 4. claim_strength 标准

| strength | 定义 | 要求 |
|---|---|---|
| strong | 会直接影响读者决策的判断 | 必须有 hypothesis_ids，并有 evidence_ids 或 limitations |
| medium | 有分析价值但不单独决定行动 | 应尽量链接 hypothesis/evidence |
| weak | 背景、线索、轻推断 | 可以只写 limitations |

## 5. 写法要求

强结论不能只写：

```text
Mizzen 值得重点投递。
```

应该写成：

```json
{
  "claim": "Mizzen 当前值得关注，但不应直接列为秋招最高优先级。",
  "claim_strength": "strong",
  "hypothesis_ids": ["H004"],
  "evidence_ids": ["E011", "E012", "E013", "E014", "E018"],
  "limitations": "客户规模、飞书集成和核心能力仍有待验证。"
}
```

## 6. 缺证据时怎么办

不要补编证据。

只能做三件事：

1. 降低 claim_strength；
2. 在 limitations 中写清楚证据缺口；
3. 回到 candidate_pool / evidence_matrix 继续补证。

## 7. Validator 检查

v0.4 validator 会检查：

- R2/R3 项目是否有 trace-manifest；
- claims 是否为空；
- strong claim 是否有 hypothesis_ids；
- strong claim 是否有 evidence_ids 或 limitations；
- hypothesis_ids 是否存在于 hypothesis_ledger；
- evidence_ids 是否能在 evidence_matrix 中找到；
- claim 或 report_section 是否能回到 final-report。

## 8. 边界

trace-manifest 不是给读者看的正文。

它是给系统、agent、validator 和未来复盘看的可信度索引。

最终报告仍然必须 reader-first，不应该把大量 ID 堆到正文前面。
